# 任务拆解与分工建议

> 对你提出的 4 段式拆解的评估，以及推荐的拆解 / 分工方案
> 配套阅读：[data_analysis.md](data_analysis.md)、[docs/task.md](../docs/task.md)

---

## 一、对原始 4 段拆解的评价

你的提议：

```
阅读理解整合  →  检索词生成  →  检索召回  →  答案决策
```

**结论：方向是对的，但颗粒度不均，几乎所有难活都被压进了"答案决策"这一段。**

### 这套拆法的优点

1. **流程是线性的**，便于团队同步进度（前一阶段产出 = 后一阶段输入）。
2. 抓住了 RAG 系统的核心骨架：理解 → 检索 → 决策。
3. 对照实际管线 `输入 → query → 召回 → 生成`，每段都有对应。

### 这套拆法的问题

1. **"阅读理解整合"语义模糊**：
   - 它指的是"理解输入题目（含图）"？还是"整合检索回来的资料"？
   - 这两件事其实分布在管线的**首尾两端**，混在一个名字里会让分工边界不清。

2. **"答案决策"承担了过多工作**：
   - 实际包含：**Prompt 工程 + Qwen-VL 推理 + 答案归一化对齐 + 多次采样/投票（可选）**。
   - 这些是整个系统**得分增长最快、调参最多**的部分，单独一人 / 一阶段难以扛住。
   - 从数据分析结论看：**题型分支 Prompt 一项就能带来 5%–15% 的分数**，比检索本身收益还大。

3. **"检索召回"在工程上偏轻**：
   - DashVector + GME-Qwen2-VL 都是现成的，主要是 SDK 调用 + 参数调优。
   - 这一段如果单独占一人，工作量会与"答案决策"严重失衡。

4. **缺少两个独立的工作流**：
   - **评估 / 误差分析**：跑通后必须看哪些题错了、错在哪一步（检索没召回？还是模型答歪了？），这是**贯穿全程的横切关切**，不属于任何单一线性阶段。
   - **工程基建**：模型加载、计时、断点续跑、`run_eval.sh` 集成、`time_cost.jsonl` 计时点埋点。**这件事必须有人盯**，否则前后端各做各的，最后拼不起来。

5. **没有显式的"题型分支"决策位**：
   - 6 种题型对管线的需求差异极大（特别是简答VQA 应该跳过检索）。
   - 如果没有人专门管"题型路由"，就会出现"一套 Prompt 打天下" / "一套检索策略适配所有题型"的次优解。

## 二、推荐的拆解方案（5 段管线 + 2 横切）

### 主管线（5 段）

```
┌─────────────────────────────────────────────────────────────────┐
│              ┌──────── 横切 A：评估 & 误差分析 ────────┐         │
│              │                                          │         │
│   ┌───────┐  ┌────────┐  ┌─────────┐  ┌─────────┐  ┌───┴────┐ │
│   │ ① 输入 │→│ ② 检索 │→│ ③ 检索  │→│ ④ Prompt│→│ ⑤ 答案 │→输出│
│   │ 理解   │  │ 词生成 │  │ 召回+重排│ │ 工程+VL │  │ 后处理 │     │
│   │ +路由 │  │        │  │         │  │  推理   │  │  +决策 │     │
│   └───┬───┘  └────────┘  └─────────┘  └─────────┘  └────────┘    │
│       │            ┌──── 横切 B：工程基建 ────┐                   │
│       │            │  模型加载 / 计时 / 落盘   │                   │
│       │            │  run_eval.sh 集成        │                   │
└───────┴────────────┴──────────────────────────┴───────────────────┘
```

### 各段职责详解

#### ① 输入理解 + 题型路由
- 解析 `question` / `image_url` / `section`
- 加载本地图片（`data/images/<basename>`），处理图缺失
- **题型分支决策**：根据 section 决定"是否检索 / 是否做图像 caption / 用哪套 Prompt"
- VQA 题可选：先用 Qwen-VL 生成一段图像描述（"这是一件商代青铜鼎，三足两耳，腹部饕餮纹…"）作为后续检索的辅助输入
- 产出：结构化的 `QueryContext` 对象（含原题、图、题型、图描述）

#### ② 检索词生成
- 文本题：从题干抽关键词，拼接选项内容（选择题尤其重要）
- VQA：题干 + 图描述
- 简答题可做 **HyDE**（让模型先猜一个答案再检索）
- 多 query 策略：每个选项独立检 + 主问题检，最后合并
- 产出：1 个或多个 query 字符串

#### ③ 检索召回 + 重排序
- 调 GME-Qwen2-VL 算 embedding（多模态 embedding，可同时编码题干+图）
- DashVector 向量检索 top-k（k=20~30）
- 可选：用 Qwen-VL 当 reranker 给每个片段打分，过滤到 top-5
- **计时点**：从构造好 query 到拿到检索结果（含 embedding + 网络）→ `retrieval_cost`
- 产出：top-k 文献片段 + 相关度分数

#### ④ Prompt 工程 + 多模态推理
- **按题型分支 Prompt 模板**（选择 / 判断 / 简答 三套，VQA 附加图）
- few-shot 示例（可从公开样例的题干部分挑，但不能用 expected_answer）
- 强约束输出格式（"只输出大写字母" / "只输出'正确'或'错误'" / "只输出短语不超过 10 字"）
- 调用 Qwen2.5-VL-7B 推理
- **计时点**：从 `model.generate()` 到拿到完整输出 → `infer_cost`
- 产出：模型 raw 输出

#### ⑤ 答案后处理 + 决策
- 用 [src/normalization.py](../src/normalization.py) 同款逻辑预校验自己的输出能否被正确归一化
- 处理判断题"双关键词陷阱"
- 自我一致性投票（temperature > 0 多次采样，对简答/VQA 有用）
- 兜底策略（检索得分太低或模型不确定时给先验答案，避免空白）
- 产出：最终 `answer` + `raw_answer`，写 `predictions.jsonl`

#### 横切 A：评估 & 误差分析
- 跑 `bash run_eval.sh`，拿到 `metrics.json`
- 按题型分组看准确率，找出薄弱题型
- 抽样 bad case：判断**错在哪一段**（检索没召回？Prompt 输出格式不对？模型答错？）
- 给每段提反馈，**持续闭环**

#### 横切 B：工程基建
- `solution/main.py` 整体骨架、参数解析、日志
- 模型 / embedding 只加载一次
- `time_cost.jsonl` 精确计时埋点
- 断点续跑（append 写盘）
- `solution/requirements.txt` 维护
- 跑通 `run_eval.sh`

## 三、4 人 / 5 人调研分工建议

### 方案 A：4 人团队

| 成员 | 主线 | 横切 | 关键产出 |
|------|------|------|----------|
| **A（数据 & 评估）** | ① 输入理解 + 路由 | A：评估 & 误差分析 | 题型路由器、bad case 分析报告、归一化对齐工具 |
| **B（检索）** | ② 检索词生成 + ③ 检索召回 | — | 多 query / HyDE、Embedding + DashVector + Rerank pipeline |
| **C（生成）** | ④ Prompt 工程 + VL 推理 | — | 6 种题型的 Prompt 模板、few-shot、Qwen-VL 调用封装 |
| **D（工程 & 决策）** | ⑤ 答案后处理 + 决策 | B：工程基建 | `main.py`、计时埋点、自我一致性投票、`run_eval.sh` 集成 |

**协作节奏**：
- 第 1 天：D 搭最小骨架（"echo 一个固定答案"也能跑通 `run_eval.sh`），baseline 出炉。
- 第 2–3 天：B、C 各自上手 → 接入 D 的骨架 → A 跑评估反馈。
- 第 4 天起：A 主导，按 bad case 分批迭代每个模块。

### 方案 B：5 人团队（推荐）

在方案 A 基础上拆出第 5 人专攻**视觉/VQA 难题**：

| 成员 | 主线 |
|------|------|
| **A** | ① 输入理解 + 路由 + 横切 A 评估 |
| **B** | ② + ③ 检索全流程 |
| **C** | ④ Prompt 工程（**QA 题型**） |
| **E（新增）** | ④ 在 **VQA / 简答VQA** 上的特化：图像 caption、视觉 Prompt、reranker 视觉打分 |
| **D** | ⑤ 后处理决策 + 横切 B 工程基建 |

**理由**：从 §1 数据分布看，VQA 占 52%，其中简答VQA（纯视觉任务）占 16%，单独有人盯能显著提升上限。

### 方案 C：3 人团队（精简）

如果只有 3 人，合并如下：

- **A**：① 输入 + ⑤ 后处理 + 横切 A 评估（"管两头"）
- **B**：② + ③ 检索全流程
- **C**：④ Prompt + VL 推理 + 横切 B 工程基建

3 人方案下放弃 reranker、放弃多次采样投票，集中火力打 baseline。

## 四、调研阶段的分头任务清单

每个方向给 1–2 个**第一周可独立完成的调研题目**，跑完后凑在一起讨论。

### 方向 A：数据与评估
- [ ] 把 50 道题按题型 + 难度（主观）打标，估算每个题型上限
- [ ] 把 `src/normalization.py` 的边界 case 整理成测试用例（覆盖判断题双关键词、简答多余前缀、多选乱序）
- [ ] 设计 bad case 抽样模板（错误归因到管线哪一步）

### 方向 B：检索
- [ ] 跑通 GME-Qwen2-VL → DashVector 的最小检索 demo，拿到 10 个样题的 top-5 召回
- [ ] 对比 3 种 query 构造法（纯题干 / 题干+选项 / 题干+HyDE 假设答案）的召回质量
- [ ] 评估 reranker 的耗时-收益比

### 方向 C：生成 / Prompt
- [ ] 跑通 Qwen2.5-VL-7B 的本地推理 + 输入图的最小 demo
- [ ] 为 6 种题型各写一版 Prompt 模板，先关闭检索做闭卷基线
- [ ] 试 few-shot 拼 1–3 条示例的效果

### 方向 D：工程
- [ ] 搭出 `solution/main.py` 骨架：解析参数 → 加载模型一次 → 循环 → 写 jsonl
- [ ] 实现 `time_cost.jsonl` 计时点（用 `time.perf_counter()`）
- [ ] 跑通 `bash run_eval.sh`，确保 baseline 不 fail 在 check_output.py 这一步

### 方向 E（如有）：VQA 专项
- [ ] 把 24 张图过一遍 Qwen-VL，看 caption 质量
- [ ] 设计"图像 caption → 拼进检索 query"实验
- [ ] 测简答VQA（识字 / 数数 / 方向）的闭卷准确率，决定是否跳过检索

## 五、关键 milestones

| 里程碑 | 目标 | 评判标准 |
|--------|------|----------|
| **M1（第 3 天）** | 跑通 baseline | `run_eval.sh` 不报错，能写出合规的 `predictions.jsonl` + `time_cost.jsonl` |
| **M2（第 7 天）** | 题型分支 Prompt + 检索接入 | 准确率明显超过闭卷基线 |
| **M3（第 12 天）** | 重排序 + HyDE + VQA 特化 | 准确率再提升一档；耗时控制在可接受范围 |
| **M4（提交前）** | 误差分析驱动迭代 + 兜底 | 没有空答案、没有归一化失败 case |

## 六、最容易踩的坑（团队同步用）

1. **模型反复加载** —— 务必 main.py 顶部一次性加载，循环里复用。
2. **判断题双关键词** —— Prompt 必须严格只输出 `正确`/`错误`。
3. **简答多余解释** —— Prompt 必须"第一行即答案"。
4. **time_cost 行数对不上** —— 计时点埋错位置或循环 break 时漏写。
5. **读了 `expected_answer`** —— 评测会 fail。代码扫一遍，确认只读 `index/section/question/image_url`。
6. **HTTP 拉图** —— 用本地 `data/images/`，评测机可能离线。
7. **写文件时机** —— 每题答完立即 append 写盘，崩了能续。
